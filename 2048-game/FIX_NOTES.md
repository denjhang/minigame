## 一、本次修复了哪些问题

### 1. 棋盘显示不全（布局缺陷）
- **现象**：4×4 网格渲染不完整，边缘方块被裁切。
- **原因**：旧代码用 `CELL_SIZE = (boardSize - SIZE * (SIZE * GAP_RATIO)) / SIZE` 计算格子尺寸，把间隙按"每个格子都带一份间隙"计算，导致总宽度超出棋盘；且背景格、间隙条（`.gap`）用绝对像素叠加，极易错位。
- **修复**：改为"内边距 + 4 格 + 3 间隙"的精确公式 `cellPx = (boardInner - 2*pad) / (SIZE*(1+GAP_RATIO) + 2*GAP_RATIO)`，背景格按 `cellPos(r,c)` 统一计算，棋盘完整显示、无裁切。

### 2. 没有过渡动画
- **现象**：移动时方块瞬间跳变，无滑动过程。
- **原因**：旧实现每步 `render()` 全量重建格子文本/类名，没有可过渡的位移。
- **修复**：
  - 每个数字块是独立持久 DOM（`.tile`），位置用 `transform: translate(x,y)` 表达；
  - CSS `transition: transform 0.12s ease` 产生平滑滑动；
  - 移动时只改 `--tx/--ty` 与 `transform`，浏览器自动补间；
  - 新增：新方块弹出动画（`popIn`）、合并放大动画（`mergePop`）、得分飘字（`floatScore`）、WebAudio 合成音效（无需外部资源，可开关）。

### 3. 方块只能向下/左/右移动，不能向上（用户报告的核心 bug）
- **原因**：旧 `move()` 用"逐格找最近邻居 + 三个分支"实现，遍历顺序对 `up` 方向计算错误，导致向上移动时方块无法滑到顶行。
- **修复**：彻底重写为 **2048 标准"压缩行"算法**（见下文"算法"）。四个方向走同一套代码，完全对称，向上移动恢复正常。

### 4. 新方块生成区域固定（用户报告）
- **说明**：生成位置本身一直是"从所有空格随机挑一个"，逻辑正确；用户看到的"固定在第 2 行"实为**向上移动失效**的连锁现象——方块堆不下行后，空格集中在中下部，看起来像固定。修复向上移动后，生成区域随棋盘分布自然变化。

### 5. 部分方块无法顺利合并（用户报告）
- **原因**：旧算法在"移动 + 合并"耦合处理时，合并承载体选错（保留了远离边缘的方块，让靠近边缘的滑入），造成合并后中间留空隙、后续合并错位。
- **修复**：`slideLine` 改为**保留靠近边缘的方块作为承载体**（位置不动、数值翻倍），让远离边缘的方块滑入后被移除。合并后紧贴边缘，无空隙。

### 6. 滑动方向判定缺陷（触摸/鼠标）
- **原因**：`slideDir = (absX > absY) ? 横向 : (dy>0 ? down : up)`，当垂直位移更大时本应判 `up/down`，但分支条件写反，`up` 方向在部分手势下丢失。
- **修复**：改为 `slideDir = (absY > absX) ? (dy > 0 ? "down" : "up") : (dx > 0 ? "right" : "left")`，垂直优先判定，四方向手势均正确。

### 7. 其它
- 头部按钮与分数牌重叠 → 头部加 `padding-right: 120px` 留位。
- 新增 `↺ 重新开始` 与 `🔊 音效开关` 按钮（旧版 `🔢` 按钮行为不明，已替换）。
- 支持方向键 + WASD + 触摸/鼠标滑动三种输入。

### 8. 只有"2"号棋子看得见，其它更大的块看不见（层叠上下文 + 写回逻辑双重缺陷）
- **现象**：用户视觉校验发现只有 2 号块可见，4/8 等更大的块看不见。
- **根因一（CSS 层叠上下文，主因）**：所有 `.tile` 都是 `position: absolute` 且未设 `z-index`，层叠顺序完全由 DOM 顺序决定——先创建的块（最早生成的 2 号）在底层，后渲染的块压在它上面。合并产生的大块虽然 DOM 更靠后，但 `.c-*` 背景类带 `linear-gradient` 会创建层叠上下文，加上之前误设的 `z-index: 1`（小于 `.score-float` 的 5）和 `will-change: transform`（强制创建层叠上下文）干扰，导致后渲染的大块反而被先渲染的 2 号块/飘字遮挡。
- **修复一（CSS）**：
  - `.tile` 去掉 `will-change: transform`，`z-index` 由 1 改为 **3**；
  - `.score-float` 的 `z-index` 由 5 降为 **2**（飘字低于方块，不再盖住数字块）；
  - `#board` 保持 `z-index: 0` 建立棋盘级层叠上下文，内部 z-index 只在棋盘内比较。
  - 层级关系：`.cell-bg`(0) < `.score-float`(2) < `.tile`(3)，数字块永远在最上层。
- **根因二（写回逻辑，残留 DOM 错位）**：`move()` 写回棋盘时，若某格 `old === placed`（同一方块原地不动），旧逻辑 `if (old) old.el.remove()` 会把它自己的 DOM 移除却不重挂载，造成"块消失"或 DOM 错位残留。
- **修复二（JS）**：
  - 写回时区分 `old === placed`（原地不动，保留 DOM 不重挂载）与 `old !== placed`（被挤走，移除旧 DOM 后重挂载新块）；
  - 取线时按 `tile.id` 去重，防御 grid 脏数据导致的同一方块被重复处理。

### 9. 不同行的方块居然合并了（"源格残留旧引用"跨行误合并，本轮核心 bug）
- **现象**：用户视觉校验发现"不同行的方块合并了"，且怀疑有看不见的方块。
- **根因（旧写回不清空源格）**：早期版本的 `move()` 在写回棋盘时，对每个目标格执行 `grid[dest] = tile`，但**从不清空该 tile 原来的源格** `grid[source]`。当某 tile 从 A 格滑到 B 格后，`grid[A]` 仍残留指向同一 tile 对象的引用。下一次移动时，另一条线（不同行/列）在快照阶段读取到 `grid[A]`，把**同一个 tile 对象**拉进自己的线里参与合并，于是出现"不同行合并"的异常，并残留"看不见"的幽灵块（其 DOM 已被移除但 grid 仍有引用）。
- **修复（两阶段：快照 → 清空 → 写回）**：重写 `move()` 为三阶段算法，彻底消除"边读边写"与"源格残留"：
  - **阶段 1（快照）**：先把每条线（行/列）的非空方块按"靠近目标边缘"顺序取出到 `lines` 数组，此后棋盘不再被读取；
  - **阶段 2（计算）**：对每条线独立执行 `slideLine`（压缩 + 相邻同值合并），得到每个存活方块的目标位置 `placements`；
  - **阶段 3（清空 + 写回）**：先把**整个棋盘置空**（`grid[r][c] = null` 全 16 格），再按 `placements` 放置存活方块。先清空再写回，保证任何 tile 最多只被一个格子引用，跨行误合并的根因被彻底铲除。
  - **阶段 4（动画结束后）**：用 `data-tid` 属性识别"被合并吸收"的 tile（其对象已不在 grid 中但 DOM 仍挂在棋盘上），移除这些幽灵 DOM，再刷新合并块外观、生成新方块、检测结束。
- **关于"过渡动画"**：CSS `transition: transform 0.12s ease` 与 `setTilePos`（同帧内更新 `--tx/--ty` 与 `transform`）本身是正确的，滑动过渡能正常触发。之前用户感觉"没有过渡动画"，实为跨行误合并导致方块跳到错误格子、视觉混乱，掩盖了平滑滑动。修复合并逻辑后，滑动过渡动画清晰可见。

### 10. 移动/合并看起来是"瞬间完成"，没有平滑过渡动画（本轮核心 bug）
- **现象**：用户视觉校验发现数字棋子移动时是瞬移、合并也是瞬时的，看不到滑动过程。
- **根因一（合并时机错误，主因）**：旧 `slideLine` 在**计算阶段**就把 `survivor.val` 翻倍并立即改 DOM 文本，`move()` 又在**滑动动画进行中**把合并块重挂到棋盘末尾（`appendChild` 使其 DOM 顺序最后、叠在最上层）。于是合并块瞬移盖住还在滑来的源块，源块滑到位时（120ms 后）才移除——视觉上源块的滑动被完全遮住，看起来就是"瞬间移动合并"。
- **根因二（CSS 层叠上下文陷阱，残留病灶）**：`.tile` 上挂的 `.c-2/.c-4/...` 颜色类都设置了 `background: linear-gradient(...)`，而**渐变背景本身就会创建层叠上下文**，把 `.tile` 的 `z-index: 3` "关"在内部使其失效。两个重叠方块（合并时）谁在上层完全取决于 DOM 顺序，与 z-index 无关。这正是第 8 项"只有 2 看得见"bug 的残留病灶——上轮只去掉了 `will-change`，没解决背景创建层叠上下文的问题。
- **修复（重写动画时序为标准 2048：先滑动 → 移除源块 → 合并块弹出）**：
  - **`slideLine` 重写**：返回 `{ items, gained }`，每个 `item = { survivor, absorbed }`。`survivor` 是**新对象**（`val` 翻倍、`isMerged=true`、**共用原 DOM `el`**），`absorbed` 是被吸收的源块对象（**保留旧值**，滑动期间仍显示旧数字）。关键：不在计算阶段改 DOM，合并块的 DOM 在滑动阶段继续显示旧值。
  - **`move()` 阶段 3（放置）**：`survivor` 先挂载（在下层），`absorbed` 后挂载（在上层，滑动期间可见旧值）；两者都 `setTilePos` 到**同一落点**，于是源块"滑进"合并块的位置，而不是被瞬间盖住。
  - **`move()` 阶段 4a（`SLIDE_MS+20` 后，滑动结束）**：移除全部 `absorbed` 的 DOM；幸存的合并块**此刻**才刷新外观（`textContent` 改新值、`className` 改新颜色、加 `.merged` 类触发弹出）。源块消失 + 合并块在落点弹出，视觉上就是"两块滑到一起 → 弹出一个新块"。
  - **`move()` 阶段 4b（再 `POP_MS` 后，弹出结束）**：`addRandomNumber` 生成新方块、解除 `isAnimating` 锁、检测游戏结束。新方块在合并动画结束后才弹出，节奏干净。
  - **CSS**：`.tile.merged` 的 `animation-delay` 由 `0.12s` 改为 `0s`（滑动结束后立即弹，不再等一个滑动周期）；`.tile` 的 `transition` 时长由 `0.12s` 对齐为 `0.13s`，与新增的 `SLIDE_MS=130` 常量一致，保证"滑动结束"回调不早于视觉滑动结束。
  - **常量**：新增 `SLIDE_MS=130`（滑动）、`POP_MS=170`（弹出），`ANIM_MS` 保留作兼容参考。
- **效果**：移动时所有方块（含源块）一起平滑滑向目标；合并时源块滑进落点、随后源块消失、合并块在落点放大弹出——完整的"滑动 → 合并弹出"两段式动画，与原版 2048 手感一致。
- **验证**：独立复现 `slideLine`/`move` 算法并跑 19 项不变量（基本合并、四方向、`[2,2,2,2]→[4,4]`、`[2,4,2]` 不合并、整列上移、survivor/absorbed 对象分离、absorbed 不入 grid、无多引用、300 次随机压力），全部通过；`vm.Script` 语法检查通过。

## 二、核心算法：压缩行（slide-and-merge）

`move(direction)` 把棋盘拆成若干"线"（横向移动取每行，纵向移动取每列），对每条线独立做"压缩 + 合并"，再写回。

```
slideLine(line):   // line[0] = 靠近目标边缘的一端
  out = []
  i = 0
  while i < len(line):
    if line[i+1].val == line[i].val:      # 相邻同值
        line[i].val *= 2                  # 保留靠近边缘者，翻倍
        line[i].isMerged = true
        out.push(line[i]); i += 2         # 被吸收者丢弃
    else:
        out.push(line[i]); i += 1
  return out
```

**为什么这样是对的**：
- 从靠近边缘的一端开始扫描，保证"先处理者优先合并"，符合 2048 规则；
- 每次遇到同值就成对消耗（`i += 2`），天然保证**一个方块一次移动最多合并一次**（`[2,2,2,2] → [4,4]` 而非 `[4,8]`）；
- 保留靠近边缘的承载体，合并后紧贴边缘、无空隙，后续移动不会错位；
- 四个方向只是"取线方式 + 边缘方向"不同，逻辑完全共用，消除了旧版按方向写死分支导致的 `up` 失效。
