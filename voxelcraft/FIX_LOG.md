# Voxelcraft — 修复记录与复盘

**项目**：`voxelcraft/`（网页版 3D 我的世界，Three.js 体素引擎）
**日期**：2026-09-22 ~ 09-23
**引擎**：Three.js r170（本地 `lib/three.module.min.js`，ES Module，无构建工具）
**运行**：`python serve.py` → <http://localhost:8471/>（**8000 端口被本机其他程序占用，切勿使用**）

---

## 背景

本项目的初版由**本地部署的中等规模模型**生成（用户描述为 Qwen3 27B 级别；
此处不代为认定具体型号与版本）。它能独立产出一份跑得起来、地形生成/破坏放置/
昼夜循环都具备的体素 MC，本身已超出"玩具 demo"的水准。
但用户实测后报出三个问题，逐一读代码定位后发现：**都是"能跑但语义错了"的类型**，
没有任何异常抛出，唯一的探测器是人眼。这份记录把三个 bug 的根因、修法，
以及本次排查中暴露的方法论问题留档。

## BUG #1 — 绝大部分方块半透明（水反而是唯一不透的）

| 项 | 内容 |
|---|---|
| **现象** | 除水以外的所有方块（草/土/石/木/沙/砖…）看起来都是半透明的，能隐约透出后面的方块 |
| **根因** | `main.js` 调用网格化函数时**第三个参数传反**。`buildChunkGeometry(world, cx, cz, true)` 的 `true` 语义是 `waterOnly`，即**只生成水**，结果被赋给了名为 `geoSolid` 的变量并绑定不透明材质；而 `false`（生成除水外的**全部地形**）被赋给 `geoWater`，绑定了 `waterMat` —— 其定义为 `transparent: true, opacity: 0.75`。于是整个世界的实心地形都在用 75% 不透明度渲染 |
| **为何静默** | 无异常、无类型错误；两个 mesh 都正常创建；三角形数量看着合理。参数是裸布尔值，调用点变量名是 `geoSolid`/`geoWater` 的非黑即白二分，反转被完全藏住 |
| **修复** | mesher 由二分布尔改成语义化三层：`'solid'`（不透明）/ `'glass'`（alphaTest 镂空）/ `'water'`（唯一半透明材质），各层在 `main.js` 绑定对应材质 |

```diff
- const geoSolid = buildChunkGeometry(world, cx, cz, true);   // true 实际只生成「水」
- const geoWater = buildChunkGeometry(world, cx, cz, false);  // false 生成「除水外全部地形」
- entry.solid = new THREE.Mesh(geoSolid, opaqueMat);
- entry.water = new THREE.Mesh(geoWater, waterMat);           // ← 全部地形套了 0.75 透明材质
+ // 三层语义化分层，各层绑定对应材质
+ for (const [name, mat] of [['solid', opaqueMat], ['glass', glassMat], ['water', waterMat]]) {
+   const geo = buildChunkGeometry(world, cx, cz, name);
+   if (geo) { entry[name] = new THREE.Mesh(geo, mat); scene.add(entry[name]); }
+ }
```

**顺带暴露的设计欠账**：原接口"水 / 非水"的二分**装不下玻璃**。玻璃被硬塞进 solid 层、
用带透明 alpha 的贴图当不透明渲染，这本身也是错的（只是错得不明显）。
修复后玻璃独立成层，用 `alphaTest: 0.5` 做镂空 —— 中间透空、白色边框可见，与原版一致。

## BUG #1b — 半透明的第二个来源：图集 mipmap 跨图块混叠 alpha

| 项 | 内容 |
|---|---|
| **现象** | 修复参数传反后，远处方块仍有整体发虚感 |
| **根因** | 纹理图集是**单行 272×16**（17 个 16×16 图块）。开启 `generateMipmaps` 后，mipmap 生成会把水（alpha=205）、玻璃（alpha=55）的 alpha **平均进相邻的不透明图块**；远处使用低层级 mip 采样时，不透明材质也会把纹理 alpha 写入画布帧缓冲，浏览器按预乘 alpha 合成 → 大片发虚 |
| **修复** | `minFilter = NearestFilter` 且 `generateMipmaps = false` |

> 注：本 bug 与 BUG #1 是两个独立原因、症状相似。只修一个都不够 —— 这也是
> "症状的合理成因"与"产生症状的代码"必须分开对待的典型例子。

## BUG #2 — 掉进水里出不来

| 项 | 内容 |
|---|---|
| **现象** | 玩家落水后无法脱身，在水中反复上下浮动 |
| **根因** | 三重叠加：<br>① 水中判定只看**身体中段**一格。脚仍在水里时中段已出水 → 切到空气物理 → 重力把人拽回水中，形成"上蹿下跳"的振荡，永远出不去；<br>② 即使上浮出水面，**游泳惯性**（vel.y≈2.8）会把人带出水面，随后重力反向拉回；<br>③ 缺少原版的游泳垂直操作 |
| **修复** | ① 改为**脚底格或中段任一在水体中**即算"在水中"（原版按身体盒与水体相交判定）；<br>② 完全离开水体时**清零垂直速度**（游泳惯性不保留到空中）；<br>③ 补充 Space 上浮 / Shift 下潜 |

```diff
- const mid = this.world.get(Math.floor(this.pos.x), Math.floor(this.pos.y + 0.5), Math.floor(this.pos.z));
- this.inWater = mid === BLOCK.WATER;
+ const fx = Math.floor(this.pos.x), fz = Math.floor(this.pos.z);
+ const feet = this.world.get(fx, Math.floor(this.pos.y), fz);
+ const mid  = this.world.get(fx, Math.floor(this.pos.y + 0.5), fz);
+ const wasInWater = this.inWater;
+ this.inWater = feet === BLOCK.WATER || mid === BLOCK.WATER;
+ if (wasInWater && !this.inWater) this.vel.y = 0;
```

## BUG #3 — 跳跃过高、滞空过久（两个 bug 叠加）

| 项 | 内容 |
|---|---|
| **现象** | 跳跃高度明显超过 1.25 格，滞空时间很长，"飘" |
| **根因 A** | **重力量纲漏乘 tick 率**。`vel` 的单位是 blocks/s，而每 tick 的速度变化应是 `0.08 blocks/tick² × 20 ticks/s = 1.6`。旧代码只减 `0.08` —— 等效重力仅原版的 **1/20** |
| **根因 B** | 物理未做固定步进。按单帧 dt 施加"每 tick 一次"的 Δv，结果随帧率漂移 |
| **修复** | ① 重力乘以 `TICK_RATE`；② 改为**固定 20Hz 步进**：Δv 与位移绑定在同一个 tick 内完成，物理结果与帧率彻底解耦；③ `JUMP_VY` 按本引擎离散模型反推为 **10.05**（连续近似 `sqrt(2gh)=8.944` 在此模型下只能跳到约 1.0 格） |

```diff
- this.vel.y -= PLAYER.GRAVITY_PER_TICK;                       // 等效重力只有原版 1/20
+ this.vel.y -= PLAYER.GRAVITY_PER_TICK * PLAYER.TICK_RATE;    // 0.08 × 20 = 1.6
```

**帧率无关性验证**（同一份代码，不同 update 步长驱动）：

| 步长 | 20 Hz | 30 Hz | 60 Hz | 144 Hz |
|---|---|---|---|---|
| 跳跃峰值 | 1.221 格 | 1.221 格 | 1.221 格 | 1.221 格 |

相机改用插值位置（`prevPos` + `alpha`），20Hz 物理在高刷屏上依然顺滑。

## BUG #4 — 水面高度方向写反

| 项 | 内容 |
|---|---|
| **现象** | 海面略高于岸边方块顶，岸边能看到水面悬空 |
| **根因** | 水面顶面的下沉量写作 `const base = isWaterTop ? 0.88 : 0;` 并在 `y + cy2 + base` 中使用 —— **加号把海面抬高了 0.88 格**，而非下沉 0.12 |
| **修复** | 改为 `-0.12`；同时把**水面侧面的顶边**也下沉 0.12，否则岸边会露出 0.12 格高的水墙 |

## 功能补充 — 创造模式飞行（依据 minecraft.wiki）

原版创造模式：**双击跳跃键**切换飞行，飞行中**跳跃键上升、潜行键下降**，再双击关闭。

- `Player.setFlying()`：进入飞行时清零下坠速度；飞行中不受重力，水平移速 10 格/秒
- 双击判定放在跳跃处理**之前**，否则第二次按下会先触发一次地面起跳
- 输入监听范围由 `locked || fallback` 放宽到含 `started`：Pointer Lock 是异步的，
  点"开始"到锁生效之间的按键原本会被静默丢弃

## 环境坑 — Chromium 启发式缓存返回旧模块

| 项 | 内容 |
|---|---|
| **现象** | 改完代码刷新页面，跑的还是旧逻辑（`minFilter` 读出来仍是旧值），一度误判"修复无效" |
| **根因** | `python -m http.server` **不发送任何 Cache-Control**，Chromium 的启发式缓存据此认为旧 `.js` 仍然"新鲜"，直接返回缓存。`?bust=` 只作用于 index.html，对模块文件无效 |
| **修复** | 新增 `serve.py`，所有响应带 `no-cache, no-store, must-revalidate`；README 改为优先推荐它 |

## 复盘

### 1. 这类 bug 的本质：能跑，但语义反了

三个 bug 没有一个会抛异常。没有类型错误、没有崩溃、画面也在动 —— 唯一的信号是
"人眼觉得不对劲"。这意味着**只要没人盯着屏幕，它就会一直存在**。把"看着对"
当成"是对的"，是这类项目最大的风险。

### 2. 症状的成因 ≠ 产生症状的代码

"方块半透明"这个现象，合理成因可以有很多：材质、光照、雾、混合模式、贴图 alpha……
第一轮排查就走了**雾**这条路（把 fog near/far 从 30/90 收到 15/45），
**修了一个并不存在的症状**。正确做法是先读产生渲染的那几行代码，
而不是从现象往回猜。

### 3. 界面设计比调用点更容易出错

原接口用裸布尔 `waterOnly` 作参数、调用点用 `geoSolid`/`geoWater` 命名 ——
二进制语义遇上非黑即白的命名，把反转藏得严严实实。而且这个二分**根本装不下玻璃**，
接口从一开始就不够用。**该质疑的是接口，不是传参那一行。**

**可操作的结论**：禁止裸 bool 标志参数出现在调用点（改具名选项或独立函数）；
当类别会增长时（水 / 玻璃 / 树叶 / 未来更多），一开始就用可扩展的表示。

### 4. 结构性断言 > 人眼

这类 bug 用眼睛看很低效。本次最终用的是一组**量化不变量**：

| 断言 | 期望 | 实测 |
|---|---|---|
| 地形三角形必须落在不透明材质上 | 透明材质承载的地形三角形 = 0 | 0（地形 49182 tris 全在不透明层） |
| 画面帧缓冲 alpha | 全 255 | min = 255 |
| 水面顶面高度 | 28.88（= 29 + 1 − 0.12） | 28.88 |
| 跳跃峰值（各帧率一致） | ≈1.25 格 | 1.221 格 @20/30/60/144Hz |
| 游泳能出水 | 脱离水体且 y > 29 | 48 帧内出水 |
| 放置/破坏 | 砖块落到目标邻格 | (48,30,47) |

专抓"渲染成功但语义错了"这一类。

### 5. 作者也会犯同样的错（本次自省）

排查过程中**我自己**写出了同类 bug：`const fullTick = dt >= 0.049;` ——
按单帧时长判断是否施加重力。60FPS 下 `dt ≈ 0.0167` 永远小于 0.049，
**重力分支永远进不去**，表现为人物漂浮、跳不起来。是我回头 review 自己的 diff 时
才发现的 —— 如果直接交付，用户看到的就是"跳不起来"，然后进入同一轮修复循环。

结论：区别不在"会不会犯"，而在频率、以及在于是**自己发现**还是**被用户发现**。
把自检（读 diff、跑不变量）变成固定动作，比提高单次正确率更可靠。

### 6. 对本地小模型的评估

用本地 27B 级别模型跑这类活，性价比最高的两条改进：

1. **消除静默语义歧义**：禁裸 bool 参数、类别用可扩展表示。这次的主 bug
   本质上是一个"接口设计给了犯错空间"的问题。
2. **配便宜的不变量检查**：它的产出常常"看着对、跑得动、语义反了"，
   而唯一能替代人眼的只有断言。工具链越干净越好 —— 缓存返回旧代码这类环境噪音，
   对推理能力更弱的作者，伤害会被放大。
