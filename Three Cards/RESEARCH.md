# Three Cards 设计调研文档

> 对标对象：**《羊了个羊》**（微信小游戏，堆叠式三消）
> 参考原型：**《3 Tiles / Tile Match》**（堆叠式三消玩法的原始范式）
> 文档目的：为自研同类小游戏（暂定名 *Three Cards*）提供玩法机制、难度设计、社交裂变与争议风险的完整调研，作为立项与实现的依据。
> 整理日期：2026-09-25
> 调研来源：百度百科、维基百科、果壳、36氪、人人都是产品经理、腾讯云开发者社区、Reddit gamedesign、Deconstructor of Fun 等（链接见文末）。

---

## 1. 一句话定义

**堆叠式三消（Stack / Three-in-a-row tile matching）**：屏幕中央是一摺**层层叠压**的图标牌，玩家只能点击**最上层、未被压住**的牌；被点击的牌落入底部一排**有限卡槽**；当卡槽中凑齐 **3 张相同图标**即自动消除；把牌池全部清空即通关。

与经典《糖果传奇》式"换位置找三连"的 Match-3 不同：本类游戏的牌**不能交换位置**，只能"从上往下、逐层解锁"，核心矛盾是**有限卡槽 vs 大量堆叠牌**带来的"选择 + 规划 + 一点运气"。

## 2. 来源与背景（为什么值得做）

### 2.1 《羊了个羊》的来龙去脉
- **开发 / 发行**：北京简游科技有限公司（开发者兼发行商），制作人张佳旭。
- **上线**：2022 年 6 月 13 日首发于微信小程序；**2022 年 9 月起在中国大陆爆火**，成为现象级；后续扩展到抖音小游戏、iOS、Android、鸿蒙等平台。
- **引擎**：Cocos2d / Cocos Creator。
- **商业背景**：吉比特通过控股子公司"厦门雷霆网络"间接持有简游科技约 20% 股权。
- **续作**：《羊了个羊：星球》2024 年 11 月获得版号，2025 年上线（引入"省份羊群"团队对抗、个人称号、地域排行榜、每日一关）。

### 2.2 玩法原型
- 玩法原型常被称为 **《3 Tiles》/ Tile Match**：牌层层堆叠 + 底部一排卡槽 + 三张相同消除（Deconstructor of Fun 对该类产品的拆解、Reddit r/gamedesign 的机制讨论均印证此范式）。
- 《羊了个羊》本身即基于该原型，因此存在"玩法抄袭《3 Tiles》"的争议。

### 2.3 它为什么能出圈（产品侧启示）
1. **玩法极简、受众广**：规则几秒看懂，消除带来即时正反馈，是典型 kill-time（碎片时间）产品。
2. **社交裂变**：道具通过"转发 / 分享"获取 → 朋友圈、群聊自发传播。
3. **地域 / 集体荣誉感**：省份"羊群"、头羊榜、全国排名，把单人游戏变成集体荣誉竞争。
4. **难度设定 + 残局悬念**：极高难度 + 疑似"无解残局"制造话题（热搜第一）。
5. **心理学钩子**：
   - "放弃吧，何苦为难自己"这类文案挑衅玩家自尊 → 激发驱动力。
   - "控制错觉 / 老虎机效应"：道具制造"也许能赢"的错觉 → 高唤醒、强动机、持续复玩。

> **立项结论**：本类游戏的壁垒不在"复杂玩法"，而在**难度曲线、社交钩子、裂变/变现机制**的设计。自研时玩法可快速复刻，重点投入难度与留存设计。

## 3. 核心玩法机制（需实现的核心）

### 3.1 基本规则
1. 屏幕中央有若干**堆叠层**，牌层层压住下方牌。
2. 玩家点击牌 → 该牌**移动到下方卡槽**。
3. 卡槽容量**固定且小**（《羊了个羊》为 **7 格**）。
4. 卡槽中**出现 3 张相同图标** → 该 3 张立即消除。
5. 场上所有牌被清空 → **通关**。
6. 卡槽**被占满且无法再消除** → **本局失败**。

### 3.2 可点击性判定（关键实现点）
- 一张牌**可点击** ⇔ 它上面（更高 z 层、且空间上压住它的位置）**没有其他牌**。
- 被压住（未解锁）的牌不可点；可选牌用**更明亮的配色 / 高亮**区分（视觉反馈）。
- 点击上层牌后，被它压住的下层牌随之解锁。
- ⚠️ 遮挡判定是堆叠坐标几何问题：需定义牌在 2D 平面的 (x, y, layer) 位置，用"是否存在更高 layer 且矩形相交（或中心在其投影内）"来判断压盖。

### 3.3 卡槽与消除
- 卡槽 = 固定长度数组（默认 7）。
- 每次点击入槽一张牌；入槽后检查是否凑齐 3 同色 → 消除腾出 3 格。
- 消除后卡槽紧凑或保持顺序（设计选择，见 4.2 待决）。
- **7 格的隐性设计**：3 格用于"即将消除的一组"，**真正自由的余量只有约 4 格**，因此容错极低（见 5.3 有解性分析）。

### 3.4 道具（每局通常各 1 次）
| 道具 | 作用 | 实现要点 |
|---|---|---|
| **撤回（Undo）** | 撤销最近一次点击，把刚入槽的牌移回原位 | 需要维护操作栈 / 状态快照 |
| **移出（Left/Right 移位）** | 把卡槽中 3 张牌移到临时侧区，腾出空间 | 侧区可再取回 |
| **打乱（Shuffle）** | 重新随机排列场上所有未消除牌的位置 | 仅打乱位置不改变牌种数量，**不能改变可解性** |
| **复活（Revive）** | 失败后恢复卡槽 / 续玩一次 | 需记录失败前状态 |

> 道具获取：分享 / 转发 / 看广告（见第 5 节商业化）。

### 3.5 失败与重开
- 卡槽满且无 3 消 → 失败弹窗（"放弃吧，何苦为难自己"类文案）。
- 选项：使用复活 / 放弃本局重开（重新随机布牌）。

## 4. 关卡与难度设计（核心竞争力所在）

### 4.1 难度曲线（《羊了个羊》的"最大胆的冒险"）
- **第 1 关 = 玩法教程**：牌少、层浅、几乎必过，目的是让玩家"以为很简单"。
- **第 2 关起难度陡增**：牌量与堆叠层数大幅增加，几乎所有人都卡在这里。
- 官方称第 2 关通过率约 **千分之一**，全网"通关率不到 0.1%"。
- 后续关卡（通关后）为每日 / 多关挑战 + 排行榜。

> 设计要点：**"第一关不可能输，第二关不可能赢"** 是刻意营造的落差，制造挫败 + 胜负欲 + 话题。

### 4.2 关键设计抉择（自研需明确）
1. **卡槽是否紧凑**：消除后左侧牌是否自动左移补齐？（紧凑更友好，非紧凑更硬核）
2. **有解性策略**（见 4.3）——这是同类游戏最大的"道德争议点"，必须做出明确选择并想清楚。
3. **牌种数量**：不同图标种类越多越难（需与牌量、卡槽容量共同调参）。
4. **堆叠方式**：手工布牌 vs 随机布牌 vs 反向生成布牌（决定难度可控性）。

### 4.3 有解性（Solvability）——核心算法与争议
- **随机乱放**的牌堆**不保证有解**：可能出现"死局"（剩余牌无法凑出任何 3 消）。《羊了个羊》被玩家质疑"故意设计成无解"，官方未明确承认存在无解。
- **如何保证有解（推荐做法）**：
  1. 先准备若干**完整三元组**的牌（每种牌数量为 3 的倍数）。
  2. 模拟"可解的消除序列"：反复随机挑一组能消除的 3 张，记录顺序。
  3. 把牌**按消除顺序的逆序**逐层摆到网格上（后摆的在上层）。
  4. 由此**必然存在**一条可通关路径（即"先摆后消"的逆过程）。
- **引入难度**：在"保证有解"的基础上加入**噪声**——
  - 打乱层序 / 位置，使解路径更隐蔽；
  - 混入"干扰牌"（数量非 3 倍数、无法完全消除的牌），让部分残局天然接近无解；
  - 卡槽余量极小（4 格自由）放大每一步的错误代价。
- ⚠️ **风险**：如果"可解"只是名义上（解路径极难找到、实际近似无解），会被玩家与媒体定性为"欺骗设计"。建议：**第 1 关保证真可解且难度低；正式关保证存在解路径，但通过层数/噪声控制实际难度**，并保留"无解即判失败 + 道具/复活"的兜底体验。

### 4.4 技巧规律（可写进游戏内"攻略/提示"，提升留存）
1. 优先消除**最顶端**的图案，看清后排再动。
2. 把下方/侧边的牌堆当"辅助暂存"，配合中间图案徐徐消除。
3. **道具牌（最下方那排）尽量留到最后**，作为挽回失误的关键一手。
4. 明牌（确定可用的）可先放一边留作备用，优先消除中间"未知部分"。

## 5. 社交 / 商业化 / 留存设计

### 5.1 社交裂变
- **省份"羊群"**：开局选择所属省份，分数计入省排名，"头羊榜"展示当日 Top3（如浙江/山东/广东）。
- **战队 / 集体荣誉**：为玩家家乡或战队而战；获胜为省份羊群"添一羊"。
- **分享得道具**：道具的获取绑定分享行为 → 朋友圈/群聊传播（本类游戏的标准套路，但非唯一爆点）。
- 本质：**不靠游戏内社交，而靠社交应用里的共同话题**（地域话题 + 难度话题）。

### 5.2 排行榜与荣誉
- 个人通关排名（单人排名）+ 全国/省份排名。
- 续作引入：个人称号（如"最快无道具通关 = 最强王者"）、实时地域排行榜、每日一关。

### 5.3 商业化（变现）
- **激励视频广告**：获取道具 / 复活机会。
- **分享 / 裂变**：获取道具（免费但拉新）。
- **品牌赞助关卡**：在关卡中植入品牌图标（爆火后被品牌方追捧，是主要变现手段之一）。
- 核心变现循环：**高难度 → 想赢 → 缺道具/复活 → 看广告或分享**。

### 5.4 留存钩子
- 极小卡槽 → 极低容错 → "就差一点"的挫败感 → 再试一次。
- "控制错觉"（道具制造可赢错觉）+ "自尊挑衅文案" → 持续复玩。
- 每日一关 + 排行榜 → 每日回访。

| 争议 | 详情 | 自研应对 |

## 7. 技术实现要点（开发清单）

### 7.1 数据模型
```
Tile {
  id: number
  type: string        // 图标种类（需为 3 的倍数个一组）
  x, y: number        // 2D 平面坐标（决定压盖）
  layer: number       // z 层，越大越在上
  state: 'board' | 'slot' | 'removed'
}
Slot { capacity: 7, tiles: Tile[] }   // 卡槽
Board {
  tiles: Tile[]
  slots: Slot
  tools: { undo: int, move: int, shuffle: int, revive: int }
  status: 'playing' | 'won' | 'lost'
}
```

### 7.2 关键算法
- **可点击性**：`isTopmost(tile) = 不存在 t' 使得 t'.layer > tile.layer 且 overlap(t', tile)`。
- **消除检测**：入槽后统计槽内 `type` 计数，任一 `type` 计数达到 3 → 移除该 3 张。
- **布牌（保证可解）**：按 4.3 的"逆消除序列摆放"算法。
- **难度调节**：层数、牌种数、噪声牌比例、卡槽容量，作为可调参数。

### 7.3 渲染
- 2D 分层绘制：按 `layer` 从低到高绘制，上层牌覆盖下层。
- 高亮：可点击牌用正常/亮色，被压牌降低亮度。
- 平台：微信小游戏（首选，对标）、抖音小游戏、Web 版（便于自测）。

### 7.4 交互与反馈
- 点击牌 → 动画飞入卡槽；3 消 → 消除动画 + 音效。
- 卡槽满 → 失败弹窗（文案 + 复活/分享/放弃选项）。
- 道具按钮（底部 3 个）+ 各 1 次使用限制。

## 8. 待定 / 需进一步确认的问题
1. **卡槽是否紧凑**（消除后是否左移补齐）？——影响手感与难度，需 A/B。
2. **牌量 / 层数 / 牌种数的具体参数表**（分关卡）——需通过"可解性生成器 + 通关率测试"校准。
3. **是否保证每关 100% 有解**，还是"部分关故意接近无解"——涉及 4.3 的合规与口碑风险，需产品拍板。
4. **美术题材**：《羊了个羊》用"食物图标"（白菜等），自研应选差异化题材。
5. **变现比例**：广告 vs 分享 vs 品牌赞助的配比与触发点。
6. **地域/战队系统**是否首版就上（增加后端复杂度：排名、省队、奖励发放）。

## 8.5 参考蓝本源码剖析（solvable-sheep-game）

> 已克隆到 `reference-solvable-sheep/`。技术栈 **Vite + React + TypeScript + SCSS**，单页应用，无后端（排行榜用 Bmob，已下线）。下面是把"可解"这个核心卖点落到代码里的关键实现，可直接迁移到 `Three Cards`。

### 8.5.1 数据模型（`src/components/Game.tsx`）
```ts
interface MySymbol {
    id: string;            // 随机 6 位字符串，唯一标识
    status: number;        // 0=在牌堆  1=在队列(卡槽)  2=已三连消除
    isCover: boolean;      // 是否被上层遮挡（不可点击）
    x: number; y: number;  // 百分比坐标（0~100 网格 + 偏移）
    icon: Icon;            // 图标（含 content/clickSound/tripleSound）
}
type Scene = MySymbol[];   // 整个牌堆就是一个数组，顺序即"层序"
```
**关键设计**：不显式存 z 层，而是用**数组顺序**隐含层序——数组里排后面的牌压住排前面的牌。`checkCover` 据此算遮挡。这是最省事的表示法。

### 8.5.2 可解性是怎么保证的（核心）
注意：该实现**并不是**用"逆消除序列摆放"的强可解算法，而是靠**构造性保证**：
- `makeScene(level, icons)` 中，图标池 `icons.slice(0, 2*level)`，**每个图标固定生成 6 张**（`for i<6`）。
- 6 是 3 的倍数 → **每种图标总数必为 3 的倍数**。
- 因此"把所有牌按任意顺序依次消除"在数量上必然能配成整组，**不存在"剩 2 张无法消除"的死牌**（前提：玩家用道具或足够耐心总能解锁）。

> ⚠️ 与 `RESEARCH.md` 4.3 节的对比：4.3 描述的"逆序摆放保证存在一条解路径"是**更强的可解保证**（保证有解路径）；而 solvable-sheep-game 只保证"牌总数按 3 取模为 0"，即**数量可清**，但具体某一步卡死仍可能，需靠**弹出/撤销/洗牌**道具兜底。做 `Three Cards` 时两者可结合：
> - 基础保证 = 每种牌数 = 3 的倍数（实现简单，本仓库即如此）；
> - 进阶保证 = 逆消除序列生成（保证真可解，见 4.3）；
> - 再配合三个道具，体验上"几乎总能通关"。

### 8.5.3 遮挡判定 `checkCover`（O(n²)，足够用）
```ts
// 牌 A 是否被 B 压住：B 在 A 之后（更高层）且两矩形相交
const { x: x1, y: y1 } = cur;
const x2 = x1 + 100, y2 = y1 + 100;      // 每张牌视为 100×100 的方格
for (let j = i + 1; j < scene.length; j++) {
    const { x, y } = compare;            // compare 在 cur 之上
    if (!(y + 100 <= y1 || y >= y2 || x + 100 <= x1 || x >= x2)) {
        cur.isCover = true;              // 两区域相交 → cur 被压
        break;
    }
}
```
- 坐标用**百分比**（`x = column*100 + offset`），100 即一张牌的边长。
- 相交判断用的是"**不重叠情况的取反**"（AABB 相交的标准写法），简洁。
- 每次点击/道具操作后都重算一次 `checkCover`，保证状态一致。

### 8.5.4 点击 → 入槽 → 三连 的主流程 `clickSymbol`
1. 若 `finished || animating` 直接 return（**动画锁 150ms**，防连点）。
2. 被遮挡或 `status!==0` 的牌点不了。
3. 置 `status=1`，push 进 `queue`（卡槽），重算 `checkCover`。
4. 等 150ms 动画，统计 `queue` 中与当前牌同 `icon` 的数量：
   - `=== 3` → 三连：`score+3`，从 queue 移除这 3 张，置 `status=2`（淡出）。
5. 判定胜负：
   - `queue.length === 7` → **失败**（卡槽满，对应原版 7 格）。
   - 场上无 `status!==2` 的牌（全消）→ 升级或胜利（`level===maxLevel` 时胜利）。
   - 否则正常 `setQueue` + `checkCover`。

**卡槽固定 7 格**（`updateQueue.length === 7` 判负），与《羊了个羊》一致。

### 8.5.5 三个道具（无限次，原版需广告/分享）
| 道具 | 实现 | 行为 |
|---|---|---|
| **弹出 pop** | `queue.shift()` 取最左一张放回牌堆底部（`y=800`），`score-1` | 腾出卡槽空间 |
| **撤销 undo** | `queue.pop()` 取最右一张放回（恢复原 x/y），`score-1` | 撤回一步 |
| **洗牌 wash** | `fastShuffle(scene)` 打乱顺序 + 重算坐标，仅对 `status===0` 的牌，`score-1` | 重排牌堆 |

> 本仓库道具**无限次且扣分**，原版是**限次+需分享/广告**。`Three Cards` 若要复刻商业闭环，应改成"限次 + 分享/广告解锁"。

### 8.5.6 难度随关卡递进
- `sceneRanges = [[2,6],[1,6],[1,7],[0,7],[0,8]]`：随 level 扩大摆放网格范围（从中心向边缘扩）。
- `offsets = [0,25,-25,50,-50]`：随 level 增加可用的偏移种类，叠得更乱。
- 图标池 `icons.slice(0, 2*level)`：关卡越高图标种类越多（更难凑对）。
- 每 5 关把已用图标再塞回池子（`while(compareLevel>0)`），持续加压。
- `maxLevel` 默认 20。

### 8.5.7 主题系统（可复用架构）
`Theme<SoundNames>` 接口（`src/themes/interface.ts`）把**图标、点击音效、三连音效、BGM、背景、深色模式、最大关卡数**全部抽成数据，换主题 = 换一个 `Theme` 对象，不改游戏逻辑。内置主题：`default`（emoji 图标）、`fisherman`（鱼）、`ikun`、`jinlun`、`pdd`（拼多多）。**`Three Cards` 可直接照搬这套主题接口**，把图标换成自己的题材。

### 8.5.8 持久化 / 其它
- `localStorage` 存 `lastLevel / lastScore / lastTime / playingThemeId`，刷新续玩（`resetScoreStorage` 在失败/切主题时清零）。
- 计时：`setInterval` 10ms 刷新，`timestampToUsedTimeString` 格式化为"X小时X分X秒(毫秒)"。
- 音效：`<audio>` 标签 + `soundRefMap` 缓存，点击/三连/道具各对应不同 `src`。
- `waitTimeout`、`randomString`、`fastShuffle` 等工具函数都在 `src/utils.ts`。

### 8.5.9 给 `Three Cards` 的落地建议
1. **直接复用**：数据模型（`MySymbol`）、`checkCover` 遮挡算法、`makeScene` 的"3 的倍数"可解构造、主题接口、计时/持久化工具——基本可照搬。
2. **必须改进**：
   - 道具改为**限次 + 分享/广告解锁**（复刻原版商业化与"控制错觉"心理钩子）；
   - 卡槽判定、连消动画要做更细腻的过渡（本仓库用 150ms 动画锁偏糙）；
   - 若要"绝对可解"，引入 4.3 的**逆消除序列生成器**替代纯"3 的倍数"构造；
   - 排行榜需自建后端（Bmob 已下线）。
3. **可解性验证**：写一个 BFS/回溯求解器（参考 `NB-Dragon/SheepSolver`）对生成关卡做离线验证，确保"真可解"，避免"伪可解"争议（见 6 节风险）。

## 11. H5 实现说明与迭代记录

> 实际可玩 H5 版本位于 `game/` 目录，纯 HTML/CSS/JS 实现（无构建依赖），用任意静态服务器即可运行。

### 11.1 项目结构
```
game/
├── index.html          # 入口：标题、棋盘、卡槽、道具、统计、结算弹窗
├── css/style.css       # 深色主题样式 + 槽位淡入动画
├── js/core.js          # 核心纯逻辑（无 DOM 依赖，Node 可离线复用）
├── js/levels.js        # 图标映射（T0..Tn → emoji）
├── js/game.js          # UI 层：渲染、交互、飞入动画、WebAudio 音效
├── test/offline-sim.js # 离线功能模拟（28 项断言）
└── backup/             # 版本备份（每次迭代前拷贝）
```

### 11.2 核心架构
- **数据模型**（`core.js`）：`Card { id, type, x, y, layer, status }`，`status` 0=牌堆 / 1=卡槽 / 2=已消除。牌堆 = `Card[]`，数组下标即隐式层序。
- **可解性**：`generateLevel` 用「逆消除序列摆放」保证每种牌数 = 3 的倍数且存在解路径；`verifySolvable` 回溯搜索对生成盘面做真可解校验，杜绝「伪可解」。
- **遮挡判定**：`computeCovered` 用 AABB 相交判断，被压牌不可点、消除后下层解锁。
- **三消闭环**：点牌入 7 格卡槽，凑 3 张相同即消除 +3 分。
- **难度递进**：20 关，随关卡增加图标种类（4→12）与牌量。
- **渲染模型**（`game.js`）：棋盘区只渲染 `status===0` 的牌，卡槽区只渲染 `slot` 中的牌，两者互不重叠 → 被点走的牌不会在棋盘与卡槽各画一次（无「数量加倍」）。

### 11.3 交互与动画
- **飞入动画**：点牌后，棋盘元素计算到目标槽位的位移，用 CSS `transform + opacity` 过渡「飞入」卡槽并淡出离开棋盘，槽内图标随后淡入（`@keyframes slot-in`）。动画时长随距离自适应（150~380ms）。
- **消除反馈**：三连时槽内图标淡出、得分 +3，播放上行三音琶音。

### 11.4 音效（WebAudio 合成，免音频文件）
用 `AudioContext` 合成，无外部音频依赖，首次用户手势后解锁：
| 事件 | 音色 |
|---|---|
| 点牌 | 三角波 660Hz 短促 |
| 入槽 | 正弦波 320Hz |
| 三连 | 523→659→784Hz 上行琶音 |
| 通关 | 523→659→784→1047Hz 四音上行 |
| 失败 | 锯齿波 330→220Hz 下行 |
| 道具 | 方波 440Hz |

### 11.5 离线验证
`test/offline-sim.js` 在 Node 环境跑核心逻辑，**28 项断言全过**，覆盖：
- 关卡生成可解性、每种牌数为 3 的倍数
- 可解性验证器自检（可解→true / 含非 3 倍数→false）
- 完整消除流程（贪心求解器对 level 1/3/6/10/14/20 全部通关，证明玩法闭环成立）
- 遮挡判定、道具状态一致性

### 11.8 回归修复记录（2026-09-26）
**现象**：刷新页面后棋盘上所有图标消失。
**根因**：
1. 新版 `render()` 改为 `if (c.status !== 0) continue;`（只画 status 0），而旧版是 `if (c.status === 2) continue;`（画 status 0 和 1）。这本身正确，但暴露了坐标越界问题。

**现象**：普通刷新（F5）后棋盘为空，必须强制刷新（Ctrl+Shift+R）才能出现卡牌。

**增量内容**（已在 core.js 中实现，但 game.js 因 bug 回退）：

1. **渐进式难度曲线**（核心逻辑增强）：

### 11.15 「点一张牌就卡死」根因修复 + 多版本端口矩阵（2026-09-27）
**现象**：最新版点第一张牌后游戏完全无响应。
**根因**：`js/game.js` 使用了**从未定义**的 `FLY_MS`（仅 `setTimeout(..., FLY_MS)` 一处引用）。strict mode 下首次点击时先置 `animating = true`，随后求值 `FLY_MS` 抛 `ReferenceError`，复位回调永不执行 → 永久锁死。RESEARCH 11.14 声称"已回退至 v7"，但 MD5 证实根目录、v7、v8 的 game.js **是同一份坏文件**——只回退了 index.html 的 `?v=` 版本号，JS 没换。
**修复**：定义 `const FLY_MS = 220`（与 `flyToSlot` 内动画时长一致），同步修 v7 目录两份副本；根 index.html 版本号 `?v=7`→`?v=9`。
**附带修复**：v2~v7 的 index.html 引用 `css/style.css` 但目录里样式是平铺的，改为 `style.css`。
**端口矩阵**（每版本独立服务，127.0.0.1 绑定）：8321=根(当前版)、8322=v2 …、8327=v7、8328=v8（v8 保留历史 bug 未修，作对照）。此前 16 个旧 http.server 挤在 8321~8326（Windows 允许端口重复绑定，请求随机落到不同目录的旧进程）是"版本混乱"的直接原因，已全部清理。
